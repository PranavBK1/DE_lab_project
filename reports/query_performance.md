## Why question (c) uses a materialized view

Computing (c) directly from `tags` × `movie_genres` (count DISTINCT users per genre and tag) takes **10,763 ms** (median of 5). `mv_popular_tags_genre` stores those counts, so the query only ranks them. Tags cannot be edited in the app, so precomputing is safe; `etl/load.py` rebuilds the view on every load. The query then takes each genre's top N from the index `mv_popular_tags_genre_rank_idx` (LATERAL + LIMIT) instead of sorting all 271k (genre, tag) rows, which spilled to disk and took about 1.5 s.

## Known issue: question (d) for blockbusters

`d_rating_distribution` reads every rating of one movie through `ratings_movie_idx`. Those rows are spread over the 1.2 GB `ratings` table, because it is stored in user order. A blockbuster's ratings sit on about 53,000 different pages (about 410 MB). This laptop has 0.8 GB of free RAM and PostgreSQL's default shared_buffers of 128 MB, so the table cannot stay in memory. Each blockbuster therefore takes 6–10 s (Forrest Gump, The Matrix, Toy Story), while a movie with a few hundred ratings stays under 1 s. In Phase 6 the table happened to be in the OS cache, which gave about 0.4 s. Fix options, each awaiting approval because each touches the 25M-row table or the (d) definition:

1. a covering index `ratings (movie_id, rating)` (about 0.5 GB, plus VACUUM after the load so index-only scans need no heap reads);
2. a 10-value rating histogram per movie in `movie_stats`, kept by the existing trigger, so (d) reads one row (no new index, the same output);
3. physically ordering `ratings` by movie (COPY sorted by movie_id, or CLUSTER), so one movie's ratings sit on a few hundred pages.
