## Why question (c) uses a materialized view

Computing (c) directly from `tags` × `movie_genres` (count DISTINCT users per genre and tag) takes **10,590 ms** (median of 5). `mv_popular_tags_genre` stores those counts, so the query only ranks them. Tags cannot be edited in the app, so precomputing is safe; `etl/load.py` rebuilds the view on every load. The query then takes each genre's top N from the index `mv_popular_tags_genre_rank_idx` (LATERAL + LIMIT) instead of sorting all 271k (genre, tag) rows, which spilled to disk and took about 1.5 s.

## Why question (d) reads a stored histogram

Counting one movie's ratings in `ratings` was slow for blockbusters: the 1.2 GB table is stored in user order, so a movie with ~80k ratings has them on about 53,000 different pages (about 410 MB). With little free RAM that took 6–10 s on a cold cache (Forrest Gump, The Matrix, Toy Story). `movie_stats.rating_hist` now stores each movie's 10 rating counts (0.5–5.0 stars), maintained by the ratings trigger and guarded by a CHECK that they add up to `rating_count` (`sql/migrations/003_rating_histogram.sql`), so (d) reads one row. The output is unchanged and is still tested against pandas.
